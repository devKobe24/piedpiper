## 지시

`.progress-report/` 의 조사 보고서를 모두 읽고,
`CLAUDE.md`를 기능별 Phase 구조로 다시 쓴다.

조사 보고서가 하나도 없으면 멈추고, 먼저 `/deep-research`를 돌리라고 안내한다.

### Phase를 나누는 기준

- 하나의 Phase는 그것만으로 테스트가 도는 단위여야 한다.
  "엔티티만 만들고 아무것도 못 하는" Phase는 쪼개기 실패다.
- 한 Phase가 한 세션 안에 끝날 크기여야 한다.
  파일 10개 이상을 건드릴 것 같으면 더 쪼갠다.
- 앞 Phase가 뒤 Phase의 전제가 되도록 순서를 잡는다.
  순환 의존이 생기면 경계를 잘못 그은 것이다.

### 완료 조건 작성 규칙

각 Phase에 **기계적으로 판정 가능한** 완료 조건을 함께 적는다.
`/goal`이 이 조건을 그대로 받아서 판정하기 때문에,
서술형으로 쓰면 판정이 불가능하고 일찍 종료될 여지가 생긴다.

| 쓰면 안 되는 것 | 써야 하는 것 |
|---|---|
| 로그인을 구현할 것 | `AuthControllerTest`가 전부 통과하고 `POST /login`이 유효 자격증명에 200과 토큰을 반환할 것 |
| API를 개선할 것 | `ProductServiceTest`가 통과하고 조회 경로에서 N+1 쿼리가 발생하지 않을 것 |
| 에러 처리를 추가할 것 | 잘못된 요청에 400과 `{code, message}` 형태의 본문을 반환하고 해당 테스트가 통과할 것 |

### 출력 형식

`CLAUDE.md`를 아래 구조로 다시 쓴다.
기존의 "확정된 결정" 섹션은 유지한다.

```markdown
## 기능 1: <이름>

### Phase 1-1: <이름>
범위: <무엇을 만드는지 한 줄>
완료 조건: <판정 가능한 조건>

### Phase 1-2: ...

## 기능 2: ...
```

### 쓰지 말아야 할 것

`CLAUDE.md`에는 **계획만** 둔다. 진행 상태(완료 여부, 날짜, 이월 항목)는
`.progress-report/state.md`에 쓴다.

`CLAUDE.md`는 매 턴 컨텍스트에 항상 올라가기 때문에,
진행 기록이 쌓이면 매 요청마다 그 토큰을 내게 된다.

### 마친 뒤

Phase 총 개수를 알리고, 첫 Phase의 완료 조건을 넣은
`/goal <조건>` 명령을 완성해서 제시한다. 직접 실행하지 않는다.
그 전에 `/ponytail full`을 켜라고 함께 안내한다.
